4. DIAGRAMA DE PROCESO — CARGA MASIVA DE EXCEL
================================================================================

DESCRIPCIÓN:
  Flujo completo desde que el usuario sube un archivo hasta que los datos
  quedan en la base de datos.

ACTORES: Usuario, Frontend, Backend (hilo principal), Backend (hilo worker),
         PostgreSQL

PASOS:

  [Usuario]
    1. Selecciona tipo documental y archivo .xlsx
    2. Hace clic en "Subir archivo"

  [Frontend → Backend] POST /api/upload/{tabla}
    3. Envía multipart/form-data con el archivo

  [Backend — hilo principal]
    4. Valida que la tabla exista en TABLES (tables_config.yaml)
    5. Calcula SHA256 del archivo
    6. Verifica en carga_archivos si el hash ya fue procesado → 409 si existe
    7. Verifica si el nombre ya existe → agrega advertencia (no bloquea)
    8. Inserta fila en carga_archivos (estado: processing)
    9. Crea job_id (UUID) en dict _jobs (memoria)
   10. Lanza hilo worker (threading.Thread)
   11. Responde { job_id } inmediatamente al frontend

  [Frontend — polling]
   12. Cada 800ms: GET /api/upload/progress/{job_id}
   13. Muestra barra de progreso y estado en pantalla

  [Backend — hilo worker: _run_upload]
   14. Estado: "reading"
       → stream_excel_chunks(): openpyxl read_only, chunks de 1000 filas
       → Mapea columnas por índice (col_map del YAML)
       → Limpia valores: None, NaN, <br>, espacios
       → Convierte columnas de fecha a INT

   15. Registra archivo en archivo_cargado (estado: pending)
   16. Guarda archivo físico en /app/uploads/{id}_{nombre}.xlsx

   17. Estado: "checking"
       → _get_catalog_ids(): obtiene id_fondo e id_subfondo desde sub_fondo
       → _seed_existing_hashes(): si la tabla no tiene hashes previos,
         calcula SHA256 de cada fila existente y los inserta en
         carga_registros_hash (solo una vez por tabla)

   18. Estado: "inserting" — por cada chunk de 1000 filas:
       a. Asigna id_fondo e id_subfondo a cada registro
       b. Calcula SHA256 de cada fila (_row_hash)
       c. Consulta carga_registros_hash → separa nuevas vs duplicadas en BD
       d. Detecta duplicadas dentro del mismo archivo (seen_in_upload set)
       e. Inserta filas nuevas en lote (INSERT ... VALUES ... RETURNING pk)
       f. Registra hashes nuevos en carga_registros_hash
       g. Vincula cada fila insertada en carga_archivo_registro
       h. Actualiza progreso en _jobs

   19. Guarda duplicados en carga_duplicados_bd y carga_duplicados_archivo
   20. Actualiza archivo_cargado (estado: done, cantidad_registros)
   21. Genera reportes Excel de duplicados en /app/exports/ si los hay
   22. Estado: "done" — escribe resultado final en _jobs

  [Frontend]
   23. Detecta status=done → muestra resumen:
       - Insertados / Omitidos BD / Omitidos archivo / Total filas
       - Detalle de filas omitidas con fila original vs fila repetida
       - Botones de descarga de reportes Excel si hay duplicados

5. DIAGRAMA DE PROCESO — AUTENTICACIÓN Y CONTROL DE ACCESO
================================================================================

DESCRIPCIÓN:
  Flujo de login y cómo se protegen los endpoints por rol.

PASOS:

  [Usuario]
    1. Ingresa username y password en LoginPanel

  [Frontend → Backend] POST /api/auth/login
    2. Envía { username, password }

  [Backend]
    3. Busca usuario en tabla usuarios por username
    4. Verifica contraseña: PBKDF2-HMAC-SHA256, 120000 iteraciones
       Formato almacenado: pbkdf2_sha256$salt$hexdigest
    5. Si OK: genera token HMAC-SHA256
       Formato: base64url(payload).base64url(firma)
       Payload: { sub, username, nombre, rol, exp (12h) }
    6. Responde { token, user }

  [Frontend]
    7. Guarda en localStorage: archivo_session { token, user }
    8. Cada request incluye: Authorization: Bearer <token>

  [Backend — cada endpoint protegido]
    9. HTTPBearer extrae el token
   10. decode_token(): verifica firma HMAC y expiración
   11. Consulta usuarios WHERE id_usuario = sub AND activo = true
   12. require_roles(): verifica que el rol del usuario esté en la lista
       permitida del endpoint → 403 si no tiene permiso

ROLES Y PERMISOS:
  admin    → todos los endpoints (lectura, escritura, eliminación, usuarios)
  operador → carga de archivos, consulta, exportación, control de archivos
  consulta → solo consulta y exportación de documentos

7. DIAGRAMA DE SECUENCIA — CONSULTA Y EXPORTACIÓN
================================================================================

DESCRIPCIÓN:
  Flujo de consulta filtrada y descarga de Excel.

  [Usuario] → aplica filtros en ConsultaPanel → clic "Buscar"

  [Frontend → Backend]
    GET /api/consultar/{tabla}
    Parámetros: page, limit, sort, order, codigo_referencia,
                titulo_formal, fecha_inicial_ano, fecha_final_ano,
                palabras_clave, id_fondo, id_subfondo

  [Backend]
    1. Valida tabla en TABLES
    2. Construye WHERE dinámico con parámetros seguros (%s)
    3. JOIN con fondo y sub_fondo para nombres descriptivos
    4. Ejecuta COUNT(*) para total de páginas
    5. Ejecuta SELECT con LIMIT/OFFSET
    6. Responde { total, page, limit, pk, column_labels, data[] }

  [Frontend] → muestra tabla paginada → clic "Exportar Excel"

  [Frontend → Backend]
    GET /api/exportar/{tabla}
    Mismos filtros, sin paginación, límite 50.000 filas

  [Backend]
    1. Ejecuta SELECT con los mismos filtros
    2. _rows_to_xlsx_bytes(): crea libro openpyxl en memoria
       - Encabezado con fondo azul oscuro (#1A3A5C) y texto blanco
       - Valores datetime con tzinfo=None (compatibilidad Excel)
    3. Responde como stream binario .xlsx con Content-Disposition

8. DIAGRAMA DE PROCESO — REVERSIÓN DE CARGA (Eliminación por archivo)
================================================================================

DESCRIPCIÓN:
  Cómo se elimina un lote completo de registros vinculados a un archivo.

PASOS:

  [Usuario — admin]
    1. En ControlArchivosPanel selecciona un archivo con estado "done"
    2. Solicita preview: GET /api/archivos/{tabla}/{id}/preview-eliminacion
       → Responde cuántos registros se eliminarán

    3. Escribe el nombre exacto del archivo como confirmación
    4. POST /api/archivos/{tabla}/{id}/eliminar-por-archivo
       Body: { confirmar: true, texto_confirmacion: "nombre_archivo.xlsx" }

  [Backend]
    5. Verifica que texto_confirmacion == nombre_archivo (exacto)
    6. Obtiene todos los id_registro de carga_archivo_registro
    7. DELETE FROM {tabla} WHERE pk = ANY(ids) con trigger de auditoría
    8. DELETE FROM carga_registros_hash (libera hashes para futura recarga)
    9. _mark_archivo_revertido():
       - UPDATE archivo_cargado SET estado='revertido', hash_archivo con sufijo :rev:{id}
       - DELETE FROM carga_duplicados_bd / carga_duplicados_archivo
       - DELETE FROM carga_archivos (libera hash para nueva subida)
       - INSERT en archivo_carga_evento (evento: 'revertido')
   10. Responde { eliminados, id_archivo, nombre_archivo, mensaje }

  RESULTADO:
    - Los registros documentales son eliminados (con auditoría)
    - El archivo puede volver a subirse (hash liberado)
    - El historial de la operación queda en archivo_carga_evento

11. DIAGRAMA DE CONFIGURACIÓN DINÁMICA (tables_config.yaml)
================================================================================

DESCRIPCIÓN:
  Cómo se añade un nuevo tipo documental sin modificar código Python ni React.

ESTRUCTURA DEL YAML:
  column_template:              ← plantilla de columnas (índice 0-based)
    nombre_columna_bd: índice_excel

  date_columns:                 ← columnas que se convierten a INT
    - nombre_columna

  tables:
    nombre_tabla_sql:
      pk:          nombre_pk
      pk_label:    "Etiqueta del PK"
      label:       "Nombre visible en UI"
      subfondo_cod: COD
      columns:     (hereda column_template si no se especifica)

FLUJO DE USO:
  1. Agregar entrada en tables → sub_fondo (SQL)
  2. Crear tabla en PostgreSQL con las mismas columnas
  3. Agregar entrada en tables_config.yaml
  4. Reiniciar backend → config.py recarga TABLES al importar
  5. El frontend obtiene la nueva tabla vía GET /api/tablas
  6. Todos los endpoints (upload, consultar, exportar) funcionan
     automáticamente con la nueva tabla

VALIDACIÓN DE SEGURIDAD:
  Los nombres de tabla en endpoints vienen del YAML (no del cliente),
  por lo que no hay riesgo de SQL injection en nombres de tabla.
